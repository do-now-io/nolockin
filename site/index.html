Sortie de secours

Partir prend un après-midi. Pas un trimestre.

Installez NoLockIn sur votre cluster Kubernetes, exportez, importez, basculez. Vos développeurs gardent la même CLI, le même manifeste, les mêmes dashboards. Seul le contexte change.

  1. Installez la plateforme sur votre clusterhelm install nolockin oci://ghcr.io/nolockin/charts/nolockin -n nolockin-system --create-namespace5 à 8 minutes · n'importe quel Kubernetes ≥ 1.29
  2. Exportez votre projet, secrets chiffrés pour la ciblenlk export --project acme --to-context mon-cluster > acme.nlkbundlejamais bridé · egress facturé 0 € · fonctionne même compte suspendu
  3. Importez : images copiées, add-ons restaurés, réplication continuenlk import acme.nlkbundle --context mon-clusterPostgres en réplication logique, Redis en replica, S3 en miroir
  4. Basculez, vérifiez, gardez 30 jours pour revenirnlk exit cutover --project acme --to mon-cluster && nlk exit verifycoupure mesurée en CI : 4 à 8 s d'écritures refusées, 0 erreur de lecture

Comment ça marche

Une couche fine sur Kubernetes, faite de projets que vous connaissez déjà.

Chaque brique est open source, choisie pour avoir une sortie standard. Rien de propriétaire sur le chemin d'une requête ni d'une donnée.

Un commit devient une image OCI

Buildpacks détectent le langage, ou votre Dockerfile. Image signée, SBOM générée, scan Trivy. Pas de runtime maison.

# nolockin.yaml · le seul fichier que vous écrivez
apiVersion: nolockin.io/v1
kind: App
metadata: { name: shop-api }
spec:                          # base commune
  source: { git: https://github.com/acme/shop-api }
  services:
    - name: web
      port: 8080
      resources: { cpu: 500m, memory: 512Mi }
  workers:
    - { name: queue, command: ["node", "worker.js"] }
  addons:
    - { name: db, type: postgres }
  env:
    DATABASE_URL: { fromAddon: db, key: url }
    STRIPE_KEY:   { fromSecret: stripe, key: secret_key }

environments:                  # un projet chacun, un overlay chacun
  staging:
    project: acme-staging
    track: main                # chaque push déploie
    services: { web: { scale: { min: 1, max: 2 } } }
    addons:   { db: { plan: single, storage: 5Gi } }
  prod:
    project: acme-prod           # pas de track : promotions seulement
    deploy:
      approval: owner
      strategy: canary
      canary: { steps: [10%, 50%, 100%], analysis: { errorRate: 1% } }
      freeze: ["Fri 16:00 - Mon 08:00 Europe/Paris"]
    services: { web: { scale: { min: 3, max: 20 }, routes: [{ host: api.acme.com }] } }
    addons:   { db: { plan: ha, storage: 50Gi } }

Un fichier, versionné avec votre code. Staging et prod dedans.

Le fichier déclare la politique : ce qui tourne, où, comment ça sort. La version déployée, elle, n'y est jamais écrite. Pas de commit « bump prod », pas de boucle de build, pas d'historique pollué.

  • Un push déploie l'environnement qui suit la branche. La prod ne suit rien : elle reçoit nlk promote, sans rebuild, le digest exact validé en staging.
  • La release se contrôle en YAML : checks CI requis, approbation d'un owner, canari analysé sur vos métriques, fenêtres de gel, previews par PR.
  • Un overlay par environnement, pas deux fichiers qui divergent. La différence prod tient en dix lignes et se relit en tant que telle.
  • Aucun champ propriétaire, les secrets jamais dedans, le même fichier sur notre cloud, sur votre cluster, sur un kind local.

Preuve

La sortie est un test d'intégration. Il bloque chaque release.

À chaque commit sur main, la CI monte deux clusters, déploie l'app de référence sur le premier avec du trafic et des écritures continues, puis exécute le protocole de sortie complet vers le second. Coupure mesurée, comptages comparés, checksums vérifiés. Si ça casse, rien ne sort.

Le rapport de ce job est publié sur cette page à chaque release. Ce n'est pas un argument marketing, c'est un artefact CI.
